How the VMware vSphere calculator works

This page walks through how the vSphere calculator turns your usage data into a VM's memory reservation, limit and shares. The reservation and limit start from the shared sizing model; this page covers what happens after that. Statements backed by VMware's documentation end with a vSphere docs link to it. Choices the documentation doesn't make for us are explained and marked Assumption, which links to its row in the table of all of them.

01 Reservation, limit and shares

  • Reservation is the guaranteed minimum allocation, in megabytes. A VM whose reservation can't be met doesn't power on, and a reservation can't be larger than the VM's configured memory. vSphere docs
  • Limit is the upper bound, in megabytes. With no limit, the VM's configured memory is its effective limit. vSphere docs The host takes memory back from VMs with the balloon driver and with host swapping. vSphere docs So a VM configured with more memory than its limit sees all of it, but past the limit that memory comes back through ballooning and swapping instead of failing fast. Assumption
  • Shares set a VM's priority against the others when memory is contended: High, Normal and Low are 20, 10 and 5 shares per megabyte of configured memory. vSphere docs

02 From usage to reservation and limit

reservation = average × (1 + request margin)                  rounded up to a whole MB
limit       = max(peak × (1 + limit margin), reservation)     rounded up to a whole MB
shares      = Normal

The margins come from the sensitivity, workload type and environment you choose; the sizing model explains them, and they are assumptions too. vSphere's MB are taken as MiB, so values pass through unconverted. Assumption

A VM whose memory reservation is above its limit fails to power on in a DRS cluster, with an InvalidArgument on memoryAllocation.reservation. So when the peak is so close to the average that the peak-based limit falls below the reservation, the limit is raised to it. Broadcom KB

Worked example

Average 390 MiB, peak 700 MiB, generic workload, medium sensitivity, production:

reservation390 MiB × 1.30 = 507 MiB507 MB
limit700 MiB × 1.30 = 910 MiB910 MB

A steady cache, averaging 1000 MiB with a 1020 MiB peak, where the reservation decides the limit:

reservation1000 MiB × 1.35 = 1350 MiB1350 MB
limit1020 MiB × 1.30 = 1326 MiB, below the reservation1350 MB

03 VMware's own guidance

VMware's advice points the other way from a tight sizing: vSphere docs

  • Reserve the minimum acceptable amount of memory, not the amount you'd like to have available.
  • A limit can waste idle memory: the VM can't use more than the limit even when the host has plenty.
  • Leave at least 10% of the host unreserved, so later changes still fit.

The calculator still gives a reservation from the average plus a margin, and a limit from the peak, because that's what it's for. It keeps VMware's advice in the note under the result: if you'd rather not cap the VM, leave the limit unlimited and the configured memory is the cap; if the reservation only needs to cover the minimum, set it lower. Assumption

04 What the calculator writes

govc vm.change -vm "<vm-name>" -mem.reservation 507 -mem.limit 910 -mem.shares normal

govc vm.change takes the memory reservation and limit in MB and the shares as a level or a number. It doesn't use -m, which would resize the VM's memory instead. govc docs The same values go in the vSphere Client under Edit Settings → Virtual Hardware → Memory.

Shares stay at Normal. The calculator has no way to know how this VM should rank against its neighbours, and doesn't claim Normal is vSphere's default. Assumption

06 What to paste

node_memory_MemTotal_bytes{instance="vm1:9100"}
  - node_memory_MemAvailable_bytes{instance="vm1:9100"}
  • Measured inside the guest with node_exporter: total memory minus MemAvailable, the kernel's estimate of memory available for new applications without swapping. Kernel docs
  • The calculator asks for guest-side numbers rather than vSphere's own "active" or "consumed" memory, which describe the host's view of the VM rather than what the guest needs. Assumption
